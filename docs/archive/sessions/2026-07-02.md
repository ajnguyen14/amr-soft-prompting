## Key Design Decisions

### Soft prompt design (previously blocking, now settled)

- **Injection modes:** both run as an ablation — internal mode is the hypothesis,
  external mode is the baseline. No longer choosing one over the other.
- **Mechanism encoding:** `nn.Embedding` lookup — single integer index →
  1280-dim vector.
- **Drug class encoding:** `nn.Embedding` lookup with sum pooling over active
  class embeddings → 1280-dim vector (drug class is multi-label, per the
  `AMRDataset` multi-hot encoding already in place).
- **Soft prompt tokens:** 2 tokens.
- **Output dimensionality:** equals `embed_dim` (1280 for the 650M training
  model) — no projection layer needed in `ESM2Wrapper`.

### Loss weighting (previously open, now resolved)

- Equal weights for V1: α = β = γ = 1.
- `BCEWithLogitsLoss` for drug class (multi-label).
- `CrossEntropyLoss` for mechanism and family (single-label).
- Tuning the weighting is explicitly deferred to V2.

### Train/val/test split (previously open, now resolved)

- Split on **ARO accessions**, not sequences, to prevent data leakage from
  multi-sequence entries.
- Stratified by resistance mechanism.
- 80/10/10 ratio.
- Fixed random seed for reproducibility.

## Implementation

### `src/models/soft_prompt.py` (`SoftPromptModule`)

Implements the settled design: `nn.Embedding(num_mechanisms, embed_dim)` for
resistance mechanism (single index lookup) and `nn.Embedding(num_drug_classes,
embed_dim)` for drug class, combined into 2 soft prompt tokens via
`torch.stack(..., dim=1)` → `(B, 2, embed_dim)`.

**Bug caught before writing the module:** the settled design's phrase "`nn.Embedding`
lookup with sum pooling over active class embeddings" was written assuming
`drug_classes` would arrive as a list of active class indices. It doesn't —
`AMRDataset` already encodes drug class as a multi-hot `(B, num_drug_classes)`
float32 vector (see `2026-06-30-esm2-wrapper.md` session, and `dataset.py`'s own
multi-label rationale). A literal index-based `nn.Embedding` lookup on that tensor
would silently do the wrong thing rather than error.

**Fix:** `drug_class_vector = drug_classes @ self.drug_class_embedding.weight` —
multiplying the multi-hot vector against the embedding weight matrix
`(num_drug_classes, embed_dim)` is mathematically identical to summing the
embeddings of the active classes, but consumes `AMRDataset`'s output directly
with no changes to the data pipeline and no padding/`torch.nonzero` complexity.
`nn.Embedding` is still the underlying learned lookup table — only the *access
pattern* changed from index lookup to matmul.
