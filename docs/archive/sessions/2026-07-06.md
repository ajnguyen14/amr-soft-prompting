## `src/eval/evaluate.py`

### Pre-implementation decisions

`amr_gene_family` has 398 classes (vs. 10 for `resistance_mechanism`, 38 for
`drug_class`) — too many for a readable confusion matrix or per-class table.
Resolved via user direction:

- `resistance_mechanism` and `drug_class`: full confusion matrix + per-class
  precision/recall/F1, rendered to PNG.
- `amr_gene_family`: aggregate accuracy + macro-F1 + top-10 most-confused
  pairs table only; the raw 398×398 confusion matrix is dumped to CSV but
  never rendered.
- Every run writes a self-contained `evaluation_results.json` (checkpoint
  path, full config, timestamp, all metrics) — the reproducibility artifact.
- No wandb logging — evaluation is a point-in-time report against an
  already-logged training run, not itself a run to log.
- Added `matplotlib==3.11.0` and `seaborn==0.13.2` to `requirements.txt`
  (previously absent) for the confusion-matrix figures.

### Implementation

- Reuses `train.py`'s `build_dataloaders`/`build_models` so eval and training
  never diverge on how data or models are constructed, and
  `src/eval/metrics.py`'s `compute_metrics` for aggregate numbers rather than
  recomputing accuracy/F1 a second way.
- `collect_predictions` concatenates raw logits/labels across the full test
  loader (unlike `train.py`'s `run_epoch`, which only needs epoch-averaged
  scalars) since confusion matrices need every individual prediction.
- CLI: `python -m src.eval.evaluate --config <path> --checkpoint <path>`;
  `--checkpoint` defaults to `<output_dir>/best_model.pt`.
- `tests/test_evaluate.py` — 7 smoke tests on the 8M model/CPU, synthetic
  fixture, following `test_train.py`'s pattern.

## GPU server diagnosis

Asked to run the real GPU training run; initial `nvidia-smi: command not
found` looked like "no GPU," but that was wrong — `lspci` confirmed two RTX
3090s present, `/proc/driver/nvidia/gpus/` confirmed both detected by the
kernel. Root cause is a driver version conflict:

- Two NVIDIA driver package sets installed side by side in `dpkg`:
  `570.211.01` and `580.159.03`.
- The loaded kernel module is `570.211.01` (`/proc/driver/nvidia/version`),
  but PyTorch's CUDA runtime is `13.0`, which needs the 580-series driver —
  hence `torch.cuda.is_available() == False` with error 804 ("forward
  compatibility was attempted on non supported HW").
- `nvidia-smi` itself isn't installed — `nvidia-compute-utils-570` shows as
  `rc` (removed, config remaining) in `dpkg`.

This is a system-level fix (driver reconciliation, likely a kernel module
reload or reboot) — out of scope for in-repo work. Aidan is looping in Prof.
Andreopolous. Saved as a persistent memory
(`project_gpu_driver_blocker.md`) so future sessions don't re-diagnose it from
scratch; re-verify with `nvidia-smi`/`torch.cuda.is_available()` before
assuming it's fixed.

Server specs recorded while diagnosing: AMD Threadripper 3960X (24C/48T),
251 GiB RAM, 2× RTX 3090 (24 GB VRAM each, no NVLink reported), Ubuntu
24.04.4. Root disk (`/`) is at 92% used, only 75 GB free — worth watching once
real training/checkpointing starts; `/data` (where the repo lives) has 2.2 TB
free.
